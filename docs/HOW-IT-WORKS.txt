1. ЗАДАЧА И ГРАНИЦЫ
--------------------------------------------------------------------------------

NetGuardian решает узкую задачу: домен резолвится в IP, который не
принимает TCP-соединение (или принимает, но TLS не проходит), из-за чего
приложение зависает или падает с сетевой ошибкой.

Инструмент:

  1) находит IPv4-адрес, который реально принимает TCP на нужном порту;
  2) закрепляет адрес за доменом в системном hosts;
  3) проверяет TLS по закрепленному адресу;
  4) при ошибке откатывает hosts к предыдущему состоянию.

Что инструмент НЕ делает:

  - не является VPN, прокси или средством обхода блокировок;
  - не меняет DNS-серверы, маршруты, firewall или настройки прокси;
  - не работает с IPv6-адресами в hosts (только IPv4);
  - не перехватывает трафик и не расшифровывает TLS.

Ключевое ограничение hosts: Windows берет ПЕРВОЕ совпадение для имени.
Поэтому чужая строка выше блока NetGuardian может полностью перекрыть
фикс. Отсюда отдельный механизм обнаружения конфликтов (раздел 9).

4. ЖИЗНЕННЫЙ ЦИКЛ ЗАПУСКА
--------------------------------------------------------------------------------

4.1. Точка входа
----------------
guardian.py импортирует netguardian.cli.main и вызывает его. В
замороженной сборке PyInstaller запускает тот же guardian.py.

4.2. Разбор аргументов
----------------------
build_parser() создает argparse-парсер с общими параметрами
(--config, --data-dir, --hosts, --lang, --json, --no-color, --verbose)
и подкомандами. Общие параметры добавлены и в основной парсер, и в каждый
подпарсер, поэтому их можно писать до или после команды.

Если команда не указана, запускается интерактивное меню (cmd_menu).

4.3. Инициализация
------------------
run():

  1. AppPaths.resolve() определяет пути;
  2. paths.ensure_directories() создает data/logs/backups;
  3. log.setup() включает файловый лог;
  4. load_config() читает routes.json (создает при отсутствии);
  5. i18n.set_language() выбирает язык: --lang -> конфиг -> системный;
  6. создается Context с Cache и HostsFile;
  7. вызывается обработчик команды.

4.4. Обработка ошибок
---------------------
main() ловит NetGuardianError и печатает сообщение с подсказкой.
Неожиданные исключения логируются и дают код 1. Ctrl+C -> код 130.
При --json ошибка выводится как {"ok": false, "error": "..."}.

--------------------------------------------------------------------------------
6. КОНФИГУРАЦИЯ
--------------------------------------------------------------------------------

6.1. Модель
-----------
parse_config() превращает JSON в dataclass-объекты Config, Settings и
Profile. Неизвестные поля профиля сохраняются в Profile.raw и
записываются обратно при сохранении (прямая совместимость).

6.2. Нормализация
-----------------
normalize_domain() принимает URL или домен:
  - отбрасывает схему, путь, query, порт, учетные данные;
  - убирает точку в конце;
  - приводит к нижнему регистру;
  - конвертирует IDN в punycode (например, münich.de -> xn--mnich-kva.de);
  - проверяет регуляркой допустимость меток.

IP проверяются через ipaddress, поддерживается только IPv4.

6.3. Валидация settings
-----------------------
  language           auto|en|ru
  local_dns          пусто/auto/system или IPv4
  dns_timeout_sec    1..30
  tcp_timeout_sec    1..30
  cache_ttl_hours    0..720 (0 = кэш выключен)
  backup_keep        1..100
  verify_after_apply bool
  stuck_states       список строк

Неизвестные ключи не ломают загрузку: они попадают в warnings и
сохраняются.

6.4. Валидация профиля
----------------------
  - имя: [A-Za-z0-9_.-], 1..64 символа;
  - domains: минимум один, дубликаты схлопываются;
  - strategy: одно из четырех значений;
  - static_first/static_only требуют static_candidates или domain_candidates;
  - domain_candidates: ключ должен входить в domains, значения — IPv4;
  - ports: 1..65535, по умолчанию [443];
  - expected_issuers и process_hints — списки строк.

Ошибка валидации -> ConfigError -> код 2 и понятное сообщение с путем
и причиной.

6.5. Сохранение
---------------
save_config() пишет JSON атомарно (fsutil.atomic_write_text), с
отступами и UTF-8. Команда lang сохраняет выбранный язык.


--------------------------------------------------------------------------------
7. РЕЗОЛВЕР И КЭШ
--------------------------------------------------------------------------------

7.1. Порядок поиска
-------------------
Resolver.resolve(domain, strategy, static_candidates, domain_candidates, ports):

  1. кэш (если TTL > 0): адрес проверяется TCP-пробой;
     мертвый адрес удаляется из кэша;
  2. порядок источников зависит от стратегии:
        static_first       static -> dns -> system
        dns_discovery_only dns -> system
        static_only        static
        system_dns         system -> dns
  3. для static-источника сначала берутся domain_candidates[domain],
     затем общий static_candidates; для каждого источника кандидаты
     проверяются по очереди;
  4. первый адрес, принявший TCP, возвращается как Resolution;
  5. результат пишется в кэш и сохраняется на диск.

7.2. TCP-проба
--------------
tcp_probe(ip, ports, timeout) открывает socket.create_connection по
каждому порту. Проверка идет по реальному TCP, а не по ping/ICMP:
блокировка ICMP не мешает.

7.3. Кэш
--------
Формат версии 3.0:
    {
      "version": 2,
      "entries": {
        "github.com": {"ip": "140.82.121.4",
                       "timestamp": 1793451609.0,
                       "source": "dns:192.168.1.1"}
      }
    }
Старый формат 2.x (просто domain -> {ip, timestamp}) читается
автоматически. Записи старше TTL игнорируются и удаляются prune().
При TTL = 0 put() ничего не сохраняет.

7.4. Системный резолвер
-----------------------
system_lookup() использует socket.getaddrinfo (AF_INET). Он учитывает
hosts, поэтому после применения фикса видит закрепленный адрес.


7.5. Маршруты GitHub и GitLab
-----------------------------
В 3.1 добавлены профили github_access и gitlab_access. У GitHub разные
адреса у web, API, raw и codeload, поэтому используется domain_candidates:
у каждого домена свой список IPv4.

Проверено 31.10.2026 (TCP + TLS, DNS 192.168.1.1):

  github.com                  140.82.121.3/4, 140.82.112.3, 140.82.113.3
  api.github.com              140.82.121.6, 140.82.112.6
  raw.githubusercontent.com   185.199.108-111.133
  gist.githubusercontent.com  185.199.108-111.133
  codeload.github.com         140.82.121.9, 140.82.112.9
  gitlab.com                  172.65.251.78
  registry.gitlab.com         35.227.35.254

Издатели: Sectigo для github.com/api/codeload/gitlab, Let's Encrypt для
raw/gist. Поэтому expected_issuers профиля github_access содержит оба
значения.

Особенность hosts: строка "185.199.108.133 github.com" — это GitHub Pages,
а не web-фронт. TLS с ней может проходить, но отдается другой сайт.
Профиль считает такую строку конфликтом и не пишет блок, пока она не
удалена или не закомментирована (либо --force).

Ограничение: если провайдер или сервис блокирует IP, hosts не помогает.
NetGuardian не подменяет IP клиента и не является VPN.


--------------------------------------------------------------------------------
8. DNS-КЛИЕНТ
--------------------------------------------------------------------------------

8.1. Зачем свой клиент
----------------------
В v2.3 вывод nslookup разбирался регуляркой. Это ломалось на
локализованной Windows, на нескольких адресах и захватывало адрес
самого DNS-сервера. В 3.0 реализован минимальный DNS-клиент.

8.2. Запрос
-----------
_build_query(domain):
  - 12-байтный заголовок: случайный ID, флаг RD, QDCOUNT=1;
  - QNAME: length-prefixed метки + завершающий 0;
  - QTYPE=A (1), QCLASS=IN (1).

8.3. Транспорт
--------------
DnsClient.query():
  - UDP на порт 53 с таймаутом;
  - проверка, что ответ пришел с ожидаемого IP;
  - проверка совпадения ID;
  - если установлен флаг TC (0x0200), повтор по TCP
    (2-байтная длина + пакет).

8.4. Разбор ответа
------------------
_parse_response():
  - проверка длины и RCODE (0 = успех);
  - пропуск question-секции;
  - разбор answer-секции с поддержкой compression pointers;
  - сбор A-записей (type=1, class=1, rdlength=4);
  - дубликаты удаляются, порядок сохраняется.

CNAME не разворачивается отдельно: резолверы обычно кладут A-записи
в тот же ответ, а если нет — сработает системный резолвер.


--------------------------------------------------------------------------------
9. РАБОТА С HOSTS
--------------------------------------------------------------------------------

9.1. Формат блока
-----------------
    # === NETGUARDIAN FIX (profile) [20261031_211500] BEGIN ===
    140.82.121.4    github.com
    # === NETGUARDIAN FIX (profile) [20261031_211500] END ===

Маркеры v2.3 совместимы: тот же формат, тот же timestamp.
MARKER_RE допускает лишние пробелы и отсутствие timestamp.

9.2. Кодировка и переводы строк
-------------------------------
load_document() читает байты и определяет кодировку:
  - BOM UTF-8 -> utf-8-sig;
  - BOM UTF-16 -> utf-16;
  - иначе utf-8, затем cp1251, затем latin-1.
Перевод строки определяется по содержимому (CRLF или LF) и сохраняется.
Комментарии и BOM не теряются.

9.3. Разбор блоков
------------------
parse_blocks() идет по строкам и отслеживает BEGIN/END:
  - вложенный BEGIN, END без BEGIN, несовпадение имени -> HostsSyntaxError;
  - строка, похожая на маркер, но не соответствующая формату, тоже ошибка;
  - ошибка останавливает операцию, файл не меняется (код 4).

9.4. Конфликты
--------------
find_conflicts() смотрит строки вне блоков NetGuardian:
  - "IP домен" с другим IP для того же домена -> конфликт.
Дополнительно apply() проверяет блоки ДРУГИХ профилей: если они
закрепляют тот же домен за другим IP, это тоже конфликт.
Без --force запись блокируется. Причина: первое совпадение в hosts
выигрывает, и фикс мог бы не сработать.

9.5. Идемпотентность
--------------------
Если для профиля уже есть ровно один блок с точно таким же набором
"домен -> IP", apply() ничего не пишет и возвращает changed=False.
Timestamp при этом не обновляется.

9.6. Атомарная запись
---------------------
fsutil.atomic_write_bytes():
  1. временный файл в том же каталоге (mkstemp);
  2. запись, flush, os.fsync;
  3. os.replace(temp, target).
На Windows os.replace атомарно заменяет файл. Прерывание процесса не
оставляет частично записанный hosts.

9.7. Резервные копии
--------------------
create_backup() копирует исходные байты в:
    backups\hosts-YYYYmmdd-HHMMSS-ffffff-<tag>.bak
Ротация оставляет backup_keep последних файлов (по mtime).
restore() принимает только файл внутри backup_dir, проверяет
кодировку/маркеры, делает страховочную копию и пишет байты атомарно.

9.8. Проверка и откат
---------------------
apply() после записи перечитывает файл и сверяет блок. При расхождении
возвращает исходные байты. CLI после apply проверяет TLS по каждому
домену; при ошибке вызывает restore(backup) (или remove(profile), если
копии не было).

10. TLS-ПРОВЕРКА
--------------------------------------------------------------------------------

inspect(domain, ip=None, port=443, timeout=5):

  - создает ssl.create_default_context() (проверка цепочки включена);
  - TCP-соединение идет на ip, если он задан, иначе на domain;
  - SNI и проверка имени — всегда по domain:
        wrap_socket(raw, server_hostname=domain)
  - из сертификата берется издатель, subject, SAN, notAfter;
  - days_left считается от текущего времени;
  - при SSLCertVerificationError возвращается verified=False и текст
    ошибки; для диагностики делается повтор без проверки, чтобы
    показать издателя (verified при этом остается False).

issuer_matches() сравнивает expected_issuers с издателем подстрокой.
Это эвристика, а не pinning сертификата.

Важно: проверяется именно закрепленный IP. В v2.3 соединение шло по
имени, и валидация могла проверять системный DNS, а не установленный
маршрут.


--------------------------------------------------------------------------------
11. СКАНЕР СОЕДИНЕНИЙ
--------------------------------------------------------------------------------

list_connections():
  - netstat -ano (text, mbcs, без окна);
  - tasklist /FO CSV /NH для имен процессов (csv-модуль).

parse_netstat():
  - берет строки TCP/TCPV6;
  - local/remote разбираются split_address:
        "1.2.3.4:443", "[fe80::1%12]:443", "*:*";
  - состояние — предпоследний токен, проверка [A-Z][A-Z0-9_]*;
  - PID — последний токен.

Состояние с цифрой (FIN_WAIT_2) — отдельный тест: в v2.3 регулярка
[A-Z_]+ его не пропускала.

find_stuck() фильтрует:
  - состояние входит в stuck_states;
  - удаленный адрес не loopback/unspecified/multicast;
  - имя процесса содержит один из process_hints.

match_profile() выбирает первый профиль, чья подсказка встречается в
имени процесса.


--------------------------------------------------------------------------------
12. ДИАГНОСТИКА
--------------------------------------------------------------------------------

diagnostics.run(domain, config, hosts):

  1. записи hosts для домена (все строки, не только блоки);
  2. системный DNS (system_lookup);
  3. локальный DNS (DnsClient.query, если local_dns задан);
  4. TCP-проверка до 8 уникальных кандидатов на 443;
  5. TLS по первому рабочему IP;
  6. системный прокси: переменные HTTPS_PROXY/HTTP_PROXY, затем
     реестр HKCU\...\Internet Settings (ProxyEnable/ProxyServer);
  7. вердикт и действие.

Вердикты:
  ok     маршрут исправен;
  hosts  запись hosts указывает на мертвый IP, при этом другой IP работает;
  dns    имя не разрешается;
  tcp    адреса не принимают TCP;
  tls    TCP есть, TLS не проходит (перехват/прокси).

Действия: ok / cleanup / apply / proxy / network. Они печатаются как
рекомендация, ничего не меняя автоматически.

13. TCPVIEW
--------------------------------------------------------------------------------

tcpview.ensure(dest_dir):
  1. если Tcpview.exe уже есть — проверяется подпись;
  2. иначе скачивается:
        https://live.sysinternals.com/Tcpview.exe
        https://download.sysinternals.com/files/TCPView.zip
     (в v2.3 был неверный регистр "Tcpview.zip" -> 404);
  3. из zip берется только basename с именем tcpview*.exe
     (защита от zip-slip), размер ограничен;
  4. файл пишется во временный .exe в целевом каталоге, проверяется
     Authenticode, затем os.replace;
  5. без валидной подписи запуск запрещен, если не указан
     --allow-unsigned.

security.authenticode_status():
  - вызывает Get-AuthenticodeSignature через powershell.exe, при
    невозможности загрузить модуль — через pwsh;
  - разбирает строки NGVALID/NGINVALID/NGERROR;
  - декодирует вывод как UTF-8, cp866 или cp1251.

security.signer_is_microsoft(detail):
  - разбирает subject сертификата на атрибуты X.500 (CN, O, L, S, C);
    учитываются кавычки, обратный слэш и multi-valued RDN (CN=a+O=b);
  - сверяет организацию (O) с точным списком: Microsoft Corporation,
    Microsoft. Регистр не важен, подстрока НЕ ищется;
  - если атрибута O нет — сверяет CN по тому же точному списку;
  - если subject не разбирается на атрибуты, возвращает False (отказ,
    а не догадка).
  - В 3.1.0 здесь искалась подстрока "microsoft", поэтому сертификат с
    O="Evil Microsoft Ltd" проходил проверку. В 3.1.1 такой subject
    отклоняется.

launch() запускает процесс; при ошибке 740 (нужно повышение) —
ShellExecuteW с "runas".

15. БЕЗОПАСНОСТЬ
--------------------------------------------------------------------------------

Модель угроз и меры:

  Угроза: повреждение hosts при сбое.
    Мера: временный файл + fsync + os.replace + проверка после записи.

  Угроза: потеря рабочей конфигурации.
    Мера: копия перед каждой записью, restore, откат при ошибке TLS.

  Угроза: подмена TCPView.
    Мера: HTTPS, Authenticode, обязательный издатель Microsoft,
    запрет запуска без подписи по умолчанию.

  Угроза: zip-slip при распаковке.
    Мера: не используется extract(); читается конкретный member,
    имя заменяется на basename.

  Угроза: случайная порча чужой записи hosts.
    Мера: удаляются только блоки с маркерами NetGuardian; конфликты
    блокируют запись.

  Угроза: работа без прав.
    Мера: ранняя проверка, UAC-перезапуск, код 3.

  Приватность: телеметрии нет. В сеть уходит только DNS-запрос,
  TCP-проверка, TLS-проверка и загрузка TCPView по команде.

--------------------------------------------------------------------------------
19. ОГРАНИЧЕНИЯ
--------------------------------------------------------------------------------

  - Только IPv4 для закрепления в hosts. IPv6-литералы отклоняются.
  - hosts действует на уровне системы, но приложения с DoH (Chrome,
    Edge, Firefox) могут его игнорировать.
  - Закрепление IP не защищает от подмены DNS на уровне провайдера и не
    заменяет VPN.
  - expected_issuers — эвристика; это не certificate pinning.
  - Адреса CDN меняются; кэш и повторный apply помогают, но фикс не
    вечен.
  - Нужны права администратора для записи hosts.
  - Exe не подписан коммерческим сертификатом; возможен SmartScreen.
  - Поддержка только Windows: используются netstat, tasklist, WinAPI,
    реестр, UAC.


--------------------------------------------------------------------------------
20. КАК РАСШИРЯТЬ
--------------------------------------------------------------------------------

20.1. Добавить профиль
----------------------
Не нужен код: добавьте объект в "profiles" в routes.json.
Минимум: domains и strategy.

20.2. Добавить стратегию
------------------------
  1. config.STRATEGIES;
  2. Resolver._strategy_order;
  3. README.txt / README.md (описание);
  4. тест в test_resolver.py.

20.3. Добавить команду
----------------------
  1. cmd_xxx(ctx, args) в cli.py;
  2. subparsers.add_parser(...) + set_defaults(func=cmd_xxx);
  3. строки в i18n.py (оба языка);
  4. тест в test_cli.py.

20.4. Добавить язык
-------------------
Добавьте словарь в i18n._STRINGS с тем же набором ключей. Тест
test_i18n проверит совпадение ключей и placeholder'ов.

20.5. Добавить проверку маршрута
--------------------------------
Расширяйте sslcheck.py или diagnostics.py; не дублируйте сетевую логику
в cli.py.
